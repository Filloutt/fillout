# FillOut — Technical whitepaper

Revision 1.1 · 2026-10-19

## 01 / Scope & release status

<p>FillOut is a visual environment for constructing, compiling and simulating Boolean circuits from two primitives: Quote, a two-input NAND gate, and Settle, a one-bit state element. The system separates circuit design from the proposed ownership and minting layer.</p><p><strong>FillOut is the first collection planned for mint on this site. OpenBook will be distributed through an airdrop. Airdrop details will be announced after the FillOut mint.</strong> OpenBook is not part of the initial mint described here.</p><p>This document specifies the current circuit engine and identifies the boundaries of the future mint integration. FillOut issuance, allocation, price and target network are specified in Section 10. Launch date and production contract addresses remain unannounced. </p><h3>Why FillOut</h3><p>FillOut turns small logic parts into circuits people can build, inspect and share. Quote supplies logic; Settle supplies memory. The working Studio makes these ideas tangible before ownership is introduced. The planned collection connects circuit construction to scarce parts through irreversible burn-to-build. OpenBook expands participation through a later airdrop. VRAM rewards remain a separate, unactivated research and implementation track.</p>

## 02 / System architecture

<p>The current design has five conceptual layers:</p><ol><li><strong>Editor:</strong> a graph of positioned nodes, ports and directed connections.</li><li><strong>Compiler:</strong> graph validation, dependency resolution and conversion into an indexed intermediate representation.</li><li><strong>Simulation:</strong> deterministic Boolean evaluation and synchronous state transitions.</li><li><strong>Serialization:</strong> an editable JSON draft and a separate binary circuit representation.</li><li><strong>Mint integration:</strong> a planned contract layer for collection ownership and issuance. Wallet connection uses a signed connection acknowledgement. Mint transactions remain unavailable until launch.</li></ol><p>Pixel artwork, cable animation and indicator glow are presentation. The Boolean engine determines signal values. Animation speed is not an execution-time measurement.</p>

## 03 / Quote, Settle & ports

<h3>Quote / NAND</h3><p>For inputs a,b ∈ {0,1}, Quote computes q = 1 − (a ∧ b). NAND is functionally complete: larger Boolean functions can be constructed using NAND gates alone.</p><table><thead><tr><th>a</th><th>b</th><th>q</th></tr></thead><tbody><tr><td>0</td><td>0</td><td>1</td></tr><tr><td>0</td><td>1</td><td>1</td></tr><tr><td>1</td><td>0</td><td>1</td></tr><tr><td>1</td><td>1</td><td>0</td></tr></tbody></table><h3>Settle / one-bit state</h3><p>Each Settle node exposes its current stored bit as a signal and has one input defining its next stored bit. For Settle j, sⱼ(t+1) = v(inputⱼ,t). All state elements update together at a simulation step. The engine does not model an asynchronous SR latch, transistor-level behavior or electrical voltage.</p><h3>Input & output pins</h3><p>An input pin supplies an editable 0 or 1. An output pin references one existing signal. These are simulation endpoints, not additional mintable component classes in this document. Connecting one input to both Quote sockets implements NOT: NAND(a,a) = ¬a.</p>

## 04 / Draft graph & validation

<p>A draft is a versioned JSON object: <code>{version:1,nodes:[…]}</code>. Every node has a unique identifier matching <code>n[0-9]+</code>, a type, finite x/y coordinates and an input-reference array. Input nodes additionally store a bit value.</p><table><thead><tr><th>Node type</th><th>Input references</th><th>Meaning</th></tr></thead><tbody><tr><td>input</td><td>0</td><td>External Boolean source</td></tr><tr><td>nand</td><td>2</td><td>Quote dependency pair</td></tr><tr><td>mem</td><td>1</td><td>Settle next-state dependency</td></tr><tr><td>output</td><td>1</td><td>Observable signal</td></tr></tbody></table><p>The current draft validator allows at most 512 nodes and coordinates in [0,2000]. References may be null in an unfinished draft. Compilation requires resolvable dependencies. At least one output is required; input and output counts are each limited to 256. These are current editor/compiler limits, not finalized mint or contract limits.</p><p>The current UI rejects imported files larger than 500,000 bytes. Structural validation and compilation are separate: a structurally valid draft can still be an incomplete or invalid executable circuit.</p>

## 05 / Compilation & signal addressing

<p>The compiler first maps node identifiers and assigns the initial signal address space:</p>

```text
index 0                 constant 0
index 1                 constant 1
index 2 … 2+I−1         external inputs
index 2+I … 2+I+S−1     current Settle state
remaining indices       NAND operation results
```

<p>Dependencies are resolved recursively. Each NAND result is appended only after its sources are available. A visiting set detects a combinational cycle. A Settle output is an already-addressed state source, so a feedback path crossing Settle is permitted.</p><p>For each NAND, operand indices are sorted as (min(a,b),max(a,b)), reflecting commutativity. This is a local normalization only: the compiler does not claim whole-graph canonicalization, Boolean minimization or a unique representation for equivalent circuits. Node order can affect operation order and final bytes.</p><p>All NAND nodes are visited, including nodes that do not feed an output. A circuit containing an invalid unused NAND dependency can therefore fail compilation. Output and next-state references are resolved after NAND traversal.</p>

## 06 / Deterministic execution model

<p>Let x(t) be the external input vector and s(t) the stored-state vector. Evaluation starts with V = [0,1,x(t),s(t)]. Each operation appends 1 − (V[a] ∧ V[b]) to V. Outputs y(t) and next state s(t+1) are selected using their source indices.</p>

```text
V ← [0, 1, …x(t), …s(t)]
for op in ordered NAND operations:
    V.append(1 − (V[op.a] & V[op.b]))
y(t)   ← V[outputSources]
s(t+1) ← V[nextStateSources]
```

<p>The evaluator requires exact input and state vector lengths and accepts only bits 0 and 1. An operation cannot reference a signal that has not yet been produced. For equal IR, input vector and stored-state vector, evaluation produces the same outputs and next state.</p><p>Editing an input immediately recomputes combinational outputs against the current stored state. Step +1 commits one state transition. Run 16 performs sixteen transitions with inputs held fixed. The simulation helper accepts runs of 1–64 steps; the UI retains up to 64 trace rows.</p>

## 07 / Feedback & timing semantics

<p>A pure combinational loop has no supported evaluation ordering and is rejected. A state element breaks the loop by making its previous stored bit available before next-state computation.</p><p>For example, connecting a Settle output to both inputs of a Quote and returning Quote to the Settle input gives s(t+1) = ¬s(t). Starting from 0, successive committed states alternate 0,1,0,1. No physical clock rate is implied.</p><p>Settle updates are simultaneous at the model level. One Settle does not see another Settle’s newly committed value within the same step. There are no modeled propagation delays, metastability, electrical hazards, analog levels, power consumption or hardware timing guarantees.</p>

## 08 / Binary format: ACDV v1

<p>The current encoder emits hexadecimal bytes using big-endian unsigned integer fields. The header is 16 bytes:</p><table><thead><tr><th>Field</th><th>Bytes</th><th>Value</th></tr></thead><tbody><tr><td>Magic</td><td>4</td><td>0x41434456 / ACDV</td></tr><tr><td>Version</td><td>2</td><td>1</td></tr><tr><td>Input count I</td><td>2</td><td>External inputs</td></tr><tr><td>Output count O</td><td>2</td><td>Observed outputs</td></tr><tr><td>State count S</td><td>2</td><td>Settle elements</td></tr><tr><td>Operation count G</td><td>4</td><td>NAND operations</td></tr></tbody></table><p>Each NAND is nine bytes: one opcode byte <code>0x10</code>, followed by two four-byte source indices. The encoder then writes S four-byte next-state source indices and O four-byte output source indices.</p>

```text
encoded length = 16 + 9G + 4S + 4O bytes
```

<p>Example: one NAND, two inputs, one output and no state uses 29 bytes. With input indices 2 and 3, the result is index 4:</p>

```text
41434456 0001 0002 0001 0000 00000001
10 00000002 00000003
00000004
```

<p>Visual coordinates, labels, artwork, current input values and simulation history are not included in this binary. The editable draft and compiled circuit serve different purposes; neither should be substituted for the other.</p><p><code>ACDV</code> is the four-byte format marker used by the circuit encoder, not a separate token or project. Keeping it preserves compatibility with exported circuits; a future format change requires an explicit version transition.</p>

## 09 / Circuit metrics

<p>Quote usage corresponds to the number of emitted NAND operations. Settle usage corresponds to the state-vector length. Input/output counts describe the interface.</p><p>For depth analysis, constants, external inputs and current-state sources begin at depth 0. A NAND result receives 1 + max(depth(a),depth(b)). Reported circuit depth is the maximum depth referenced by an output or a next-state input. This is logical dependency depth, not measured latency or gas cost.</p>

## 11 / Burn-to-build circuit NFTs

<p>Creating a circuit NFT irreversibly burns its required Quote and Settle parts. A successful transaction must validate the netlist, determine exact component quantities, burn the creator's authorized balance and issue the immutable circuit record atomically. If any operation fails, the entire transaction must revert. No burned parts are recoverable.</p><p>Each circuit belongs to one processor collection. A FillOut circuit can participate independently; an OpenBook circuit can participate independently. Holding or combining both collections in one circuit is not a mining requirement. A future composition mechanism must separately define how circuits interoperate.</p><p>Burning and NFT issuance do not automatically establish mining eligibility. A circuit must satisfy the applicable task and verification rules. The burn-to-build contracts must be implemented, reviewed and deployed before circuit NFT creation is enabled.</p><p>The final storage design must specify whether executable IR is stored on-chain or supplied as transaction/event data with a commitment. A hash alone cannot recover a netlist or execute it. Maximum circuit size, data availability and worst-case validation gas must be benchmarked before burn activation; the Studio's 512-node limit is not an on-chain capacity claim.</p>

## 12 / VRAM research & verification

<p>VRAM is a proposed ecosystem reward token; mining is not active. Studio simulation creates no rewards. FillOut is intended as a higher-weight processor tier and OpenBook as a base tier; exact coefficients and eligibility remain unfinalized.</p><h3>Identity and copying</h3><p>A netlist hash identifies exact encoded bytes. It can detect a replay of those bytes, not equivalent logic, originality or authorship. Reordering nodes, redundant gates and alternate encodings may produce different hashes. Published netlists can be copied. Burning more parts is not proof of useful work and must not automatically increase task score.</p><h3>Verification authority</h3><p>No production task verifier, scoring authority or dispute system has been selected or deployed. Any initial operator-run verifier would be a centralized trust dependency and must be named, with its permissions and appeal process, before use. Exhaustive truth-table testing is feasible only for bounded small circuits; 256 inputs cannot be exhaustively enumerated. Larger or stateful tasks need a published bounded test/proof specification, security assumptions and adversarial review.</p><h3>Economic specification required before activation</h3><p>Total supply, issuance cap, emission schedule, utility, processor weights, task scoring, reward settlement and abuse controls remain undecided. No token-demand source or market value is established by this document. These parameters must be published and reviewed together before mining activation; no numeric hash power, daily yield or reward balance should be inferred from part counts.</p>

## 13 / Team circuits & reward use

<p>The 10,000 team parts have no vesting lock. The team commits not to sell these parts and to use them exclusively for circuit construction, where the components are burned. This commitment must not be represented as a contract-enforced transfer prohibition unless the published implementation enforces it.</p><p>VRAM earned by team circuits is allocated <strong>50% to VRAM liquidity support and 50% to platform operations, development and community activities</strong>. Liquidity provision is manual; the allocation does not imply automatic market purchases, automatic liquidity, a price floor or guaranteed support.</p><p>This policy applies only to team-circuit rewards, not to users' rewards. Treasury transactions and the team's circuit identifiers should be published for inspection. Any administrative permissions must be disclosed individually from the final contracts; there is no unspecified unlimited team right hidden behind a general reservation-of-rights statement.</p><p>Full public sell-out would generate 7 ETH in gross mint receipts, before costs. This is a scenario, not an operating-budget guarantee. Development funding, expenditure and runway need separate disclosure; future VRAM rewards are not assured cash funding. Liquidity support requires counterpart assets and does not create guaranteed token demand.</p>

## 14 / Security model & trust boundaries

<p>Current executable checks cover draft structure, duplicate identifiers, reference resolution, vector lengths, bit values and combinational-cycle detection. These checks do not prove correctness of a future contract deployment.</p><p>Browser storage can be cleared or unavailable. Exported drafts provide a separate copy; they are not automatically uploaded or synchronized. Import validates JSON structure rather than executing embedded code.</p><p>Wallet connection requests a public account and a signed connection acknowledgement, verified against the selected address. A readable message signature confirms the browser connection. Connection does not request token approvals or transactions. A future production flow must distinguish connecting an address, signing a message, granting approval and sending a payable transaction. A safety warning from a wallet should be investigated, not bypassed.</p><p>No independent audit is claimed. Contract-source verification, implementation review, adversarial testing and published permissions remain separate release checks. Neither this document nor a successful browser simulation establishes contract safety.</p><h3>Launch gates and permissions</h3><p>Before enabling paid mint, publish the final source, deployed addresses, constructor values, independent security review and remediation status. No completed audit is claimed today. Disclose owner, upgrade, pause, price, supply and withdrawal permissions individually, with controlling addresses and whether they are single-key or multisignature. A general team commitment is not a contract restriction.</p><p>FillOut launches with its own published issuance rules, circuit-building mechanism and deployment parameters. Contract addresses and permissions will be announced before the corresponding features are enabled.</p>

## 15 / Verification plan

<p>The production release should be reproducible from the published source, compiler settings and constructor parameters. Deployment evidence must link the published bytecode and addresses to the reviewed source release.</p><ul><li>Engine: truth-table checks, deterministic execution, state-transition ordering and rejection of invalid dependencies.</li><li>Serialization: fixed encoding vectors, lengths, source-index bounds and version handling.</li><li>Mint contracts: unauthorized calls, supply and allocation boundaries, payable-value checks, phase changes, failure rollback and callback behavior.</li><li>Integration: account/network changes during a flow, failed reads, pending/rejected transactions and independently readable transaction outcomes.</li></ul><p>This is a release verification plan, not a claim that the next production implementation has passed these checks.</p>

## 16 / Non-goals & limitations

<p>FillOut’s present simulator is a discrete Boolean model. It does not provide physical synthesis, silicon fabrication, timing closure, transistor simulation, compute rental or guaranteed financial returns. VRAM mining is a planned protocol layer and is not currently active.</p><p>Graph equivalence, dead-code elimination and global canonical ordering are not implemented by the current compiler. The editor’s 512-node bound is a editor limit and cannot be used to infer blockchain capacity or transaction costs.</p><p>Production availability, integrations and mint conditions will be documented as they become concrete. Deferred features and collections should not be treated as active functionality.</p>
